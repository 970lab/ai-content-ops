# Lessons from operating the workflow

These are paraphrased lessons from internal content work. They describe observed failure patterns and the practices adopted in response. They are not controlled performance studies, verified platform diagnoses or guarantees that every tool will behave the same way. Private source records stay outside this repository.

| Observed problem | What we changed | Check before continuing |
| --- | --- | --- |
| A technically accurate draft missed the author's actual point | Ask the author for the surprising result and intended feeling before polishing | Author recognizes their own point in the opening |
| A writing helper invented experiences and emotions to sound natural | Provide an explicit claim list and forbidden inferences; retain the original response and corrected revision | Every added experience has a source or is removed |
| Old-topic details leaked into a new script | Send a self-contained brief naming current scope and inputs | Title, cover, script and notes refer to the same story |
| Several revisions left competing “final” files | Keep one current pointer with revision and next action; retain labelled history | A new helper can find the selected draft without rereading chat |
| Current claims lacked current footage | Save the draft and put a short filming list next to it | Actual media demonstrates the exact claim/version |
| UI input/focus problems produced partial requests | Stop after inspecting the mismatch; verify the active task, exact request and returned text | A visible sent request and actual response exist; no queued fragments remain unaccounted for |
| English copy linked to a card with the wrong visible language | Review rendered cards in both the editor and public surface | Text, destination, metadata and visible image agree |
| A platform notice named broad possible quality issues | Preserve the notice and revise specific observable weaknesses without pretending to know the ranking cause | Separate observed restriction from causal hypotheses |
| A model attachment matched its packaged checksum but had a truncated internal structure | Check file-format integrity and actual opening separately from checksum equality | A matching hash proves file identity, not a valid or usable model |
| A local file or upload status was treated as downstream completion | Track source, draft, public readback and archive receipt separately | The intended recipient can access the exact delivered revision |

## Recovery patterns

**Wrong facts in a polished draft.** Freeze affected downstream assets. Mark the specific unsupported sentence, return to the source brief, produce one corrected draft and recheck its title and cover. Do not regenerate the whole project when one claim can be fixed.

**Missing media.** Continue copy organization and shot planning. Record precisely what to capture and what it must show. Do not reconstruct a missing real event with generated footage. Resume from the selected draft once actual files arrive.

**Unreliable UI or unavailable integration.** Record the observed error and current saved state. If the intended action is uncertain, inspect before retrying; repeated submissions may create duplicates. A manually copied approved brief is a valid fallback. Do not assume a queued message ran, and do not bypass a platform restriction by changing tools.

**Login required.** Save the current draft and identify the exact account/login step. Let the account owner authenticate through the official interface, then resume from the saved version. Do not request passwords in the content package.

**Attachment fails repeatedly.** Preserve the original and isolate a working copy. Verify both transport integrity (hash/size) and format validity with an appropriate reader. A supplied checksum may describe an already broken file. Compare any repair with the intended version and geometry; a repaired file is a new candidate, not proof of slicing, physical fit or load testing.

**Partial upload or review queue.** Record which files and item IDs are confirmed. Reopen the item before retrying to avoid duplicate projects. Keep draft, scheduled, review-pending and public states distinct. An unrelated successful upload does not close the failed one.

**Platform requirements changed.** Recheck the official current requirement for that destination, adjust only the affected adapter/package, and retain the evidence of the change. Never infer that a model file, render, sliced project and real printed object are equivalent forms of verification.

**No useful changed source.** Save `no_candidate` with scope and checkpoint. Do not pad a content calendar with internal maintenance notes.

**Archive unavailable.** Preserve originals and the local final package, record the intended destination and missing receipt, then retry only the unconfirmed transfer when access returns. Do not call it archived or delete local copies.

## What remains unproven

The creator guide still needs independent onboarding trials. We have not established a cross-tool success rate, typical end-to-end time, guaranteed cost saving or audience/revenue uplift. UI recovery is an operational fallback, not a reliable autonomous publishing connector.
